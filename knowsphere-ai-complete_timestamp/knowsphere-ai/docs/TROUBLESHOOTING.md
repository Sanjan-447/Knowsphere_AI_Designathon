# Troubleshooting Guide

Every issue below was actually encountered and fixed during this
project's development — not hypothetical scenarios.

## "Everything worked yesterday, now migrations are failing / documents fail to embed"

**Check**: is a `ProviderConfig` row's `capability` field set correctly?
A provider with `capability='llm'` will never be selected for embedding
generation, and vice versa. If you're getting connection errors to an
LLM-only endpoint's `/embeddings` path, this is almost certainly it — see
`app/documents/tasks.py`'s `_resolve_embedding_provider()` and
`app/chat/rag_service.py`'s `_resolve_default_provider()`, both of which
filter on capability specifically because of a real bug this caused
during Phase 3/6 development.

## `flask db migrate` wants to drop `ix_document_chunks_embedding_hnsw`

This was a recurring false-positive through Phases 2-4 (Alembic's
autogenerate didn't know about an index created via raw SQL) and was
**fixed at the source** in Phase 5 by declaring the index on the
`DocumentChunk` model itself. If you see this again, something changed
the model's `__table_args__` index declaration out of sync with the real
database index — compare them directly rather than just deleting the
autogenerated drop line and moving on.

## New migration fails against an existing (non-empty) table

Check whether the new column is `nullable=False` without a
`server_default`. This has bitten this project twice (the `capability`
column in Phase 3, the `had_error` column in Phase 5) — Alembic's
autogenerate doesn't add a `server_default` automatically, and a
straight `NOT NULL` add-column against a populated table fails outright.
Add `server_default=sa.false()` (or the appropriate literal) by hand to
the generated migration.

## Chat answers are always "not available in the enterprise knowledge base"

1. Is a document actually uploaded and `status: ready`? Check
   `GET /api/v1/documents/{id}` or the Documents page.
2. Is retrieval filtering out everything? Check whether `filters`
   (department/source_type) in your request actually match any document.
3. **This is expected, not a bug**, if you're on the dev-only local
   embedding provider (`local-deterministic-dev-only`) — its similarity
   scores are hash-based, not semantic. Configure a real embedding
   provider (OpenAI, Gemini, or an OpenAI-compatible endpoint) if
   retrieval quality matters, not just pipeline correctness.

## Chat responses seem to be reused / stale

The response cache (`app/retrieval/response_cache.py`) caches
non-streaming answers for 10 minutes, keyed by question + role + top_k +
filters. If you changed a document and expect an immediately different
answer to the same question, that's the cache — it's deliberate (see the
README's caching explanation), not a bug. Wait out the TTL, or restart
Redis in dev if you need to force a clear.

## Rate limit errors (429) during local testing/scripting

The login endpoint is limited to 10 attempts/minute per IP (brute-force
protection). If you're scripting many logins in quick succession (e.g. a
load test, or a bad retry loop), you'll hit this — it's working as
intended. This is also why the test suite explicitly disables rate
limiting in `TestingConfig` (see `app/config.py`) — many tests logging in
different users from the same test-client "IP" would otherwise trip a
limit meant for a single real client.

## Uploads getting rejected for a file that "should" work

Since Phase 6, uploads are validated against their **actual content**
(magic-byte signature), not just the file extension — a `.pdf` that's
actually plain text gets rejected. If a genuinely correct file is being
rejected, check `app/security/file_validation.py`'s
`_EXPECTED_MIME_TYPES` mapping; some office formats (docx/xlsx) are
technically zip archives and libmagic can occasionally report a slightly
different but valid MIME string — the check already accepts a few
variants per format for this reason, but a very unusual file might need
an additional accepted MIME added.

## Docker Compose: frontend can't reach the backend

Check `VITE_API_BASE_URL` was set **at build time**, not just in the
running container's environment — Vite bakes this into the compiled JS
bundle (see `frontend/src/vite-env.d.ts` and any `src/api/*.ts` file).
Changing the env var on an already-built image does nothing; you need to
rebuild.

## Test suite runs fine as `pytest tests/unit` but hangs as `pytest tests/`

This is a known, previously-debugged issue (see
`backend/tests/conftest.py`'s comments) — running unit/integration/e2e as
**separate invocations** avoids a subprocess-teardown interaction that
caused intermittent hangs in one combined run. This is the recommended
way to run the suite (and how CI should be structured), not a workaround
for something still broken.

## "Connection refused" to Postgres/Redis after a sandbox/VM restart

If you're running Postgres/Redis as services rather than via Docker,
remember they don't survive a reboot automatically unless enabled — run
`service postgresql start` / `redis-server --daemonize yes` (or your
platform's equivalent) before starting the backend or running tests.

## LangSmith "Test connection" always fails

Check the obvious things first: correct API key, correct project name.
If those are right and it still fails, check your network can actually
reach `api.smith.langchain.com` — some corporate/sandboxed networks
block it, in which case tracing genuinely cannot work regardless of
configuration until that's allowlisted.
